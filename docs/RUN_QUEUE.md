# Shared Run Queue (Claude <-> Codex <-> Jake)

This is the live queue for proposed Quantule Mapper runs, simulations, post-processing checks, validation tasks, and design gates. Its job is to stop useful tests from being lost in conversation.

Any agent may append or clarify a row. Jake selects what actually runs and chooses the lane unless the current task explicitly authorizes a run.

## Agent Instructions

### When To Add A Row

Add a row whenever a run, test, check, or analysis is:

- proposed as useful;
- mentioned as "maybe later";
- blocked on a design decision;
- deferred after an active run;
- identified as a hardening task;
- suggested as a Colab candidate;
- required to close a documented evidence gap.

Do not wait for a task to be fully specified before banking it. Use `TBD` for unknown fields and link the best available reference.

### When Not To Start A Row

Agents may append rows, clarify rows, and update evidence links. Do not move a row to `ACTIVE` unless:

- Jake explicitly selects it;
- the current prompt explicitly asks you to run it;
- or it is already part of the active handoff you were asked to continue.

Do not silently replace a selected run with a different one. If the queued row is underspecified, stop and report the missing decision.

### Status Vocabulary

Use exactly these status values unless there is a short parenthetical clarification:

```text
PROPOSED -> QUEUED -> ACTIVE -> REVIEW -> DONE
                    -> DROPPED
                    -> BLOCKED(gate)
```

- `PROPOSED`: worth remembering, not yet selected.
- `QUEUED`: selected or ordered, but not running.
- `ACTIVE`: currently running locally, in Colab, or under direct analysis.
- `REVIEW`: run completed; results are waiting for interpretation or archive verification.
- `DONE`: reviewed and documented.
- `DROPPED`: intentionally abandoned; reason must be in the row.
- `BLOCKED(gate)`: cannot proceed until a named decision, prerequisite, or scientific gate is resolved.
- `BACKLOG`: allowed only for legacy imported rows; prefer `PROPOSED` for new rows.

### Lane Vocabulary

Use one of these lane values:

```text
cpu
local-gpu
colab-a100
design
blocked
TBD
```

Lane guidance:

- `cpu`: post-processing, static analysis, manifest prep, documentation, small comparison scripts.
- `local-gpu`: short/medium trusted GPU jobs, jobs needing broad repository context, local validation, or jobs already running locally.
- `colab-a100`: targeted preregistered heavy jobs, reproduction runs, grid/timestep refinement, independent A100/JAX hardware checks, and high-value rows expected to benefit from burst compute.
- `design`: no run yet; write or resolve a design/physics contract first.
- `blocked`: gate or decision required before selecting an execution lane.
- `TBD`: lane is genuinely unknown.

Avoid `colab-a100` for broad hunts, jobs with many dynamic dependencies, jobs that cannot checkpoint useful partial results, or jobs likely to exceed Colab session limits.

### Colab Fast-Lane Requirements

Rows marked `colab-a100` should eventually point to:

- a JSON manifest under `colab_jobs/`;
- explicit source/config allowlists;
- expected outputs;
- Drive result path;
- result archive review location under `colab_jobs/results`;
- comparison or acceptance contract.
- Colab push target: whether to preserve exact arguments, run only a short pilot, increase `T`, refine grid/box, use an aggressive resource profile, or leave the row unchanged.

Use `colab_jobs/COLAB_CAPSULE_AGENT_GUIDE.md` and `colab_jobs/README.md` for the packaging workflow.

Important workflow distinction:

- A `colab-a100` row is a dispatch ticket for the fast-lane deployment workflow, not an instruction for the currently engaged research agent to stop and run it.
- The row should contain enough context that a fresh deployment agent can package, validate, hand off, and later return a result capsule by checklist.
- Research agents should normally treat Colab rows as "in the shop" until Jake returns an archive or explicitly asks that agent to prepare or review the capsule.
- Returned packages, not dashboard states, are what research agents should assess scientifically.

### Scope And Fidelity Contract

Every row must state both `execution scope` and `fidelity requirement`.

This prevents agents from optimizing the wrong thing. For example, a queue handoff test may still require a full-fidelity scientific reproduction if the point is to test whether the queue can dispatch a real Colab job.

Use these terms where possible:

```text
execution scope:
  package-only
  local-analysis-only
  smoke-test
  full-fidelity simulation
  design-only
  review-only

fidelity requirement:
  exact reproduction
  scientific source unchanged
  copied-module variant only
  diagnostic-only, no dynamics changes
  procedural UI test only
  design contract only
```

If a row says `full-fidelity simulation`, do not replace it with a toy or shortened procedural job for performance reasons. The Colab fast lane is already the performance optimization. If runtime is a concern, report the concern and ask Jake before reducing fidelity.

### Runtime And Trial Contract

Every executable row must state an estimated runtime and a stop rule. This is especially important for Colab rows because a "workflow test" can either mean a five-minute UI smoke test or a full scientific reproduction that occupies an A100 for hours.

Use these run classes where possible:

```text
package-only
ui-smoke
short-scientific-pilot
full-reproduction
full-campaign
review-only
design-only
```

Default interpretation:

- If Jake asks for a "trial", "UI test", "UX test", "handoff test", or "workflow test", assume `ui-smoke` or `short-scientific-pilot` unless the prompt explicitly requests full-fidelity science.
- If a row is `full-reproduction` or `full-campaign`, the next action must say the expected runtime before launch.
- If the expected runtime is over 30 minutes, do not let the handoff rely on `J1` label alone. Put the estimate in the queue row, manifest metadata, operator instructions, and notebook button label where possible.
- If runtime class and fidelity conflict, stop and report the conflict instead of optimizing silently.

Recommended stop-rule wording:

```text
If no new log output appears for 30 minutes, or runtime exceeds the declared upper bound without checkpoint/archive progress, stop and return logs for review.
```

### Colab Push Target

Every `colab-a100` row must state how far the Colab version is allowed or expected to push beyond the local/default run. This is the field that prevents low-resource A100 sessions from becoming accidental underpowered reruns.

Use concise phrases such as:

```text
exact args only
short pilot only
increase T to <value>
refine grid to <N/L/dt>
aggressive resource profile only
max-safe A100; archive <=5GB
not applicable
TBD; decide before packaging
```

Do not hide scientific scale changes inside a manifest. If Colab should use a longer duration, larger grid, larger box, denser cadence, larger HDF5/NPZ field-snapshot sample, or batched physics path, write that request in this queue column and then mirror it in the manifest arguments/operator instructions. Opening another Colab tab is allowed for independent jobs; do not pack unrelated runs into one capsule just to use more of a single session.

### Row Quality Rules

Keep rows short. Put details in linked handoffs, catalogs, manifests, reports, or design notes.

Every row should include:

```text
queue id / run name
status
lane
priority / order
runtime estimate / stop rule
colab push target
execution scope
fidelity requirement
reason / question
tests & gates
baseline / reference data
scripts / entrypoint / command
inputs / allowlist
expected outputs / review artifacts
Colab capsule / manifest
next action / blocker
owner / requester
reference docs
last updated
```

If a field is unknown, write `TBD`. Do not leave the implication hidden in chat history.

### Column Intent

The table is deliberately wider than a normal planning table. Fill enough columns that another agent can pick up the row without rereading chat history.

- `queue id / run name`: stable short name. Use catalog IDs when available, such as `ALIAS-1`.
- `status`: current lifecycle state from the vocabulary above.
- `lane`: expected execution lane.
- `priority / order`: rough ordering such as `after D4`, `high`, `low`, or `TBD`.
- `runtime estimate / stop rule`: expected local or Colab runtime, basis if known, and when an operator should stop and return logs.
- `colab push target`: for Colab rows, how far the A100 run should push resources or scientific scale; for non-Colab rows use `not applicable`.
- `execution scope`: whether the row is package-only, smoke-test, full-fidelity simulation, design-only, local-analysis-only, or review-only.
- `fidelity requirement`: whether the row must preserve exact scientific source/arguments, may use copied-module variants, is diagnostic-only, or is only a procedural UI test.
- `reason / question`: the smallest scientific or infrastructure question the row answers.
- `tests & gates`: pass/fail criteria, acceptance thresholds, or named design gate.
- `baseline / reference data`: prior run, frozen baseline, CSV/report, or `none`.
- `scripts / entrypoint / command`: runnable script or planned command. For Colab, this should become the manifest stage entrypoint.
- `inputs / allowlist`: required source/config/reference files or dependency closure.
- `expected outputs / review artifacts`: result files that prove the row completed and can be reviewed.
- `Colab capsule / manifest`: manifest path, notebook path, Drive result path, or `not needed`.
- `next action / blocker`: immediate next step or the named blocker.
- `owner / requester`: Jake, Claude, Codex, or specific handoff if known.
- `reference docs`: links or filenames that explain the row.
- `last updated`: date of the last queue edit.
